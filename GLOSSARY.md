# Tali Glossary

The shared vocabulary for Tali's domain and architecture. Use these terms in
code, issues, tests, and docs. See `docs/adr/` for the decisions behind them.

## Auth

### Password

The human secret typed into a Tali form. It exists only in the browser and is
never sent to the API, logged, or stored anywhere. The UI requires at least 12
characters; there are no composition rules. See
[ADR-0001](docs/adr/0001-client-side-password-kdf.md).

_Avoid:_ using "password" for anything sent over the wire — that is the
**Login Key**.

### Login Key

The browser-derived credential that replaces the password on the wire:
`argon2id(password, KDF Salt, { m: 19456 KiB, t: 2, p: 1, dkLen: 32 })`,
encoded as unpadded base64url (43 characters). It is password-equivalent in
transit, so it only travels over TLS and is never logged. `RegisterInput` and
`LoginInput` carry a `loginKey`, not a password.

### KDF Salt

The deterministic argon2id salt:
`SHA-256("tali:kdf:v1:" + normalizeEmail(email))`. Deterministic so login needs
no pre-login request (and no account-existence probe). It is **not** the
per-user `credentialSalt` stored in D1.

### Credential Verifier

The value stored in `users.credential_verifier`:
`SHA-256(credentialSalt || Login Key)`, hex, compared in constant time. The
per-user random `credentialSalt` (16 bytes, hex) prevents a shared precomputed
table across accounts. A database dump yields nothing replayable as a login.

### Rate limit

The D1 fixed-window counter (`login_attempts`) keyed by normalized email + client
IP: five failed logins per 15 minutes are allowed; the next attempt is answered
with `429 RateLimited` before any credential comparison.

## Preferences

### Display Preferences

The per-user settings in `user_preferences`: **Time Zone** (IANA), **Week
Start** (Saturday/Sunday/Monday), **Digits** (Persian/Latin), **Dashboard
Section Order** (a full permutation of the known dashboard sections), and
**Checked Item Placement** (`bottom`/`inPlace`). The server is the source of
truth; the browser keeps a read-only cache for offline boot. They do **not**
ride the sync outbox. See
[ADR-0002](docs/adr/0002-preferences-server-of-record-local-cache.md).

_Avoid:_ "user settings" for auth/profile fields — those live on `users` and
change through the auth routes.

### Week Start

The first day of the displayed Jalali week: `saturday` (default), `sunday`, or
`monday`. It drives `jalaliWeek()` and the month grid; it is presentation only,
never a date-storage convention.

### Digits

How numerals are displayed: `persian` (default, ۱۲۳) or `latin` (123). Domain
values always stay plain numbers/ISO strings; only rendering localizes them.

## Calendar

### Event

Something that happens at a specific time and shows up on the calendar: an
appointment, a meeting, a trip. An event is **timed** (two UTC instants) or
**all-day** (one local calendar date) — never both — and it carries its own
**Time Zone**, so a device that changes its zone never moves a stored event.

_Avoid:_ "appointment" or "meeting" for the entity itself — those are events.

### Occurrence

One appearance of a recurring event. A recurring event is **one** row; its
occurrences are computed from its recurrence rule by the expansion engine, not
stored. The occurrence's key is its local start date (`YYYY-MM-DD`) in the
event's time zone.

### Exception

A deviation of a single occurrence from its series: `delete` (the occurrence
does not happen) or `override` (it happens, with its own title/time/place).
Exceptions live inside their event's `exceptions` list — "this occurrence
only".

### Edit scope

Which part of a recurring series an occurrence edit applies to: **this
occurrence** (one exception on the same row) or **this and following** (a
[series split](#series-split)). A one-off event has no series, so both scopes
edit the event itself.

### Series split

The write behind "this and following": the old event row is truncated with an
inclusive `until` the day before the edited occurrence, and a new row starts at
the occurrence with the (edited) timing, rule and later exceptions. Both rows
are written in one batch and each has its own sync version and feed entry.

### Projected occurrence

An occurrence generated by the expansion read model rather than stored as a row
(`projected: true`). Projected occurrences are read-only: only the series row is
edited, deleted or synced.

### Occasion

An annual important date (a birthday, an anniversary) that usually needs
preparation. It is not an event: it is one **origin local date** plus its zone,
projected onto its Jalali month/day every year (Esfand 30 clamps to Esfand 29 in
a common year), and events may be created from it. Its **advance reminder** is
an offset expanded at read time, not a stored per-year rule, materialised once
per occurrence into the Reminder aggregate's table. See
[ADR-0008](docs/adr/0008-occasion-origin-date-and-advance-reminder.md).

### Recurrence Rule

The structured rule that makes an event or a task repeat — frequency,
interval, optional by-fields, and an end (never / count / until). It is a
JSON object, **never** an RRULE string: the month and year fields are Jalali,
which string RRULE parsers do not implement. See
[ADR-0004](docs/adr/0004-event-timing-and-exception-storage.md).

## Reminders

### Reminder

A standing intention to tell its owner something at a time — "take your
medication at 08:00", "the bin goes out on Tuesday". It carries a **Tier**, a
**Repeat**, the next **Fire** instant, a **Reminder Link** to the task, event or
habit it is about, and an optional **Silence**.

_Avoid:_ "notification" for the reminder itself — that is the delivery.

### Tier

The delivery class derived from a reminder's kind: `critical` for medication,
`normal` for everything else. It is never chosen by hand. Critical fires bypass
**Quiet Hours**; the only way to quiet one is a per-reminder **Silence**.

### Fire

One occurrence of a reminder becoming due: the instant `fire_at` passes. A fire
is a fact about the calendar, not about the network; a reminder can fire without
anybody being told.

### Dispatch

One attempt to tell the owner about one **Fire**, recorded as a ledger row before
anything is sent. It has two axes: **delivery** — `push_outcome` is *pending*,
*accepted* (the push service took it), *failed* (transient, retryable) or
*expired* (no further attempt) — and the **answer** — `response` is `done`,
`snooze` or `dismiss`. A dispatch is **owed** while it has no response and has not
expired. The dispatch ledger, not the push, is the truth about whether a reminder
happened. See [ADR-0005](docs/adr/0005-reminder-firing.md).

### Claim

Writing the dispatch row that makes a fire *this* sweep's responsibility. One
claim per (reminder, fire instant, origin) is enforced by the ledger's unique
key, and the claim batch advances the series' `fire_at` under a compare-and-set,
so a repeated, late or overlapping sweep cannot notify twice or skip an
occurrence.

### Sweep

The once-a-minute pass that claims due fires, then pushes every owed dispatch
whose **Deliver At** has arrived. The policy runs at claim time; the sweep itself
just compares `deliver_at`. It is a catch-up query rather than a timer: nothing
is scheduled ahead, so nothing is lost when the Worker is down.

### Quiet Hours

The owner's 23:00–07:00 local window in which normal-tier fires do not push. A
held fire is an owed dispatch whose **Deliver At** is the end of the window; it
is shown in the inbox on the next app open and flushed at 07:00. Critical fires
skip the window. The window is fixed in Must; the settings UI is deferred (#13).

### Overnight Queue

The normal-tier dispatches held back inside **Quiet Hours**. They are not a
message queue and not a second store: a held dispatch is an owed dispatch whose
**Deliver At** is the end of the window. Medication-tier fires never enter it.

### Deliver At

The instant a dispatch may actually be pushed, chosen by the policy when the fire
is claimed: the fire instant or the end of **Quiet Hours**. A **Silence** produces
no dispatch at all. The sweep compares one column and asks no further questions.

### Silence

`Reminder.silencedUntil` — the point past which the whole series may fire again.
Fires inside the silence produce no dispatch; the series advances past it, and
setting the silence expires any dispatch already owed. It is the only way to quiet
a medication reminder, and it is a different thing from a **Snooze**.

### Snooze

"Tell me again in X minutes", for one occurrence only (5, 10, 15, 30 or 60). It
closes the current dispatch as answered `snooze` with a compare-and-set (so a
double tap opens one child) and opens a new one at `now + X`; the series'
schedule does not move. A snoozed fire is not held by **Quiet Hours** — asking
again is consent (ADR-0005 §5; a derived default pending owner confirmation).

### Missed Inbox

The list of dispatches that are due and unanswered — whether or not a push ever
reached a browser. It is derived from the ledger, so "delivered but ignored" and
"browser was closed" land in one place, and nothing leaves it by being deleted:
after 24 hours from `scheduledFor` an unanswered dispatch moves from the inbox
view to history.

### On-time

The adherence measure: a dispatch is on-time when it was answered `done` at or
before 30 minutes after its **root** fire instant (an early `done` counts).
Snoozed-then-done is *late* because the grace window does not restart at the
snooze; a dismiss or an unanswered dispatch is not on-time.


## Habits

The vocabulary of the habit log and its statistics. `docs/streak-algorithm.md`
is the normative spec for **Expected Day**, **Streak Period**, **Satisfied
Period**, **Streak**, **Best Streak** and **Success Rate**; see also
[ADR-0006](docs/adr/0006-habit-shape.md) (the shape) and
[ADR-0007](docs/adr/0007-habit-streak-periods.md) (the streak).

### Habit

A repeating intention the user wants to keep up (walk, read, take the
medication). It carries a title, optional description, colour/icon, a
**Frequency**, an optional local reminder time and its own **Time Zone** — and
no streak: the streak is derived from the habit's **Habit Entries** by
`docs/streak-algorithm.md`.

_Avoid:_ "streak" as a stored field on a habit, or "task" for a habit — a task
is done once; a habit is kept up.

### Frequency

How often a habit is meant to happen: **daily**, **selected weekdays** (a
non-empty, duplicate-free set of ISO weekdays) or **X times per week** (1–7).
It is a union, never a free-text rhythm, so the three shapes cannot be mixed.

### Frequency Era

One history entry of a habit's **Frequency**: the local date that frequency
took effect. Era 0 is the habit's **Started On** date; a change opens the next
era at the first period boundary after the period it changed in, and is never
back-dated, so eras never overlap and a day's stats are always judged against
what the habit asked for *then* (FR-HAB-03's edge case). The last era always
equals the current frequency.

### Started On

The owner's local date a habit began. It is a stored domain fact (`startedOn`),
not the `createdAt` instant, because the day a habit began must not move when
the owner changes time zone. Streaks and statistics never look before it.

### Habit Entry

One day's log of one habit: `done`, `partial` or `missed`, keyed by
`(habitId, localDate)`. It is a separate row, not a field on the habit, so a
tap is one idempotent upsert and a 7/30/90-day window is one range scan. The
entry keeps the zone its day was written in. A day with no entry is **blank**;
blank and Missed are different records (one is silence, the other an answer),
even though neither earns credit.

_Avoid:_ "log row" or "check-in" in user-facing language.

### Logged Day

The local calendar date a **Habit Entry** covers, in the entry's own **Time
Zone**. "Today" is the owner's wall date, never UTC's, and a backdated day is
still the day the user says it was.

### Backdating Window

The seven days before today, plus today, on the user's own local calendar. A
tap inside the window logs that day; a tap outside it is refused with a typed
error rather than clamped. Logging never reaches into the future.

### Status Cycle

The order a repeated tap walks a **Habit Entry** through: Done → Partial →
Missed → Done. Because a day is one row for all time, a tap replaces the day's
status; it never adds another row.

### Revive

Bringing a tombstoned **Habit Entry** back by tapping its day again. The same
row comes back — same id, same creation time, same owner — on the logging
mutation's compare-and-set path. The generic sync push keeps tombstone-wins, so
a queued offline tap that meets a tombstone recovers through that explicit
mutation.

### Expected Day

A day on which a habit is due: every day for a daily habit, the selected days for
a weekday habit. Only expected days can extend or break a **Streak**; every other
day is transparent. An X-times-a-week habit has no expected days — its commitment
is a quota over a **Streak Period**.

_Avoid:_ "scheduled day" for the X-times-a-week case — nothing is scheduled.

### Streak Period

The unit a **Streak** counts: one local day for daily and weekday habits, one
Saturday–Friday week for X-times-a-week habits. The counting week is fixed by the
product and is **not** the display **Week Start**.

_Avoid:_ "week" unqualified when the counting week is meant; say **Streak
Period** or "counting week".

### Satisfied Period

A period that met its commitment: one Done or Partial on an expected day, or X
Done/Partial days inside a counting week. A closed period that is not satisfied
breaks the streak; an open period never breaks it and advances it as soon as it
is satisfied.

### Streak

The number of consecutive **Satisfied Periods**, in the unit of the last counted
period — days for daily/weekday habits, weeks for X-times-a-week habits; a period
keeps its unit after a frequency change, so the badge still reads days for the
few days before a new weekly era begins. It ends with the open period once it is
satisfied, or with the last closed satisfied period while the open one is still
short. It always travels with its unit.

_Avoid:_ "chain", "run" and "combo" in UI copy; and never a bare number whose
unit is unspecified.

### Best Streak

The longest **Streak** visible in the current entries, kept **per unit** (best
days, best weeks), because a day run and a week run are not comparable. It is
recomputed, not stored, so a correction that un-satisfies a past period can lower
it as well as raise it; it still survives a frequency change, because the old
unit's periods remain in the entries.

### Success Rate

How much of the commitment was met inside a window: the average of the weighted
share of each qualifying week's quota (X-times-a-week habits) or the weighted
share of expected days (daily/weekday habits), with Partial counting half and the
result capped at 100%. It answers "how fully", while the **Streak** answers "did
you keep it up at all". The two may disagree on purpose. It is computed for the
current unit and is `null` when no period qualifies — the UI then shows the open
period's progress.
