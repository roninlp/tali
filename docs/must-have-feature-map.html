1Executive summary

What “Must” means here: a complete, shippable product for two users where every daily planning action works end to end, including offline and two-device sync.

🧩

27 must features

25 numbered FR items with the Must badge, plus account/shared-space and offline sync as cross-cutting Must obligations.

💡

Two mirrors

Each feature is expressed as backend (data, services, jobs) and frontend (screens, interactions, state) work so neither side is forgotten.

⏳

Five slices

Foundation → Core Planning → Time & Reliability → Habits & Notes → Hardening. Each slice leaves the app fully usable.

Release criterion for the Must version

Both users can plan, track, and review a full week using only this product: create account, see “Today”, manage tasks/lists/events/reminders/habits/notes, check off shared shopping lists live on two devices, receive medication reminders, and export nothing (export is “Should”, not Must).

2Chosen robust stack (non-negotiable for this visualization)

As requested: Turborepo monorepo, the complete Effect suite on the backend, Alchemy v2 for infrastructure as code, SolidJS v2 (RC) on the frontend.

MonorepoTurborepo + pnpm workspacesBackend & frontend shared

Pipeline-based task graph (build, test, lint, deploy), shared TypeScript config, shared domain package, content-addressed remote cache. One change to a domain schema type-checks every consumer.

Must-have consequences
  • One shared package defines every entity schema, ID, validation rule, and sync cursor used by both apps.
  • Feature flags and release slices are toggled at the package boundary, not by copying code.
BackendEffect — full suiteRobust by default

Effect as the runtime and effect system, with @effect/schema for all domain types, @effect/platform for HTTP/RPC and runtime config, @effect/sql for database access, @effect/workflow for long-running jobs, plus Effect’s observability, retry, and concurrency primitives. Typed errors, dependency injection via Layers, and deterministic resource cleanup are the robustness.

Why this is “robust” here
  • Schemas are the single source of truth for wire format, DB mapping, validation, and client types — no drift between frontend and backend.
  • Errors are part of the type signature of every service method, so reminder delivery and sync failure modes are handled explicitly.
  • Layers make the reminder scheduler, DB pool, auth service, push gateway, and sync engine composable and testable with fake implementations.
  • Structured concurrency prevents half-finished sync jobs and leaked DB connections under partial failures.
InfrastructureAlchemy v2 (IaC)Reproducible cloud stacks

Alchemy v2 provisions the whole runtime: API worker/container, database (Postgres via Hyperdrive or the chosen managed DB), R2/S3 object storage, queues, cron triggers, and secrets. Every environment (dev, staging, prod) is declared in typed TypeScript and diffed on deploy.

Must-have consequences
  • Reminder scheduling (cron) and Web Push credentials are infrastructure, not ad-hoc server state.
  • Backup/export buckets and retention are declared alongside the app, not configured by hand.
  • Rollback is a deploy, which matters while iterating on sync and recurrence bugs.
FrontendSolidJS v2 (RC) + Vite-based SolidStartFine-grained reactivity

Solid v2 RC components compile to fine-grained reactive DOM updates, with @solidjs/router, @solidjs/meta, and SolidStart for routing, SSR/streaming, and server functions. State lives in signals and stores; mutations are optimistic by construction.

  • Today dashboard re-renders only the changed habit/calendar item, which is what makes <100ms interaction p95 realistic.
  • Complex screens (weekly view, month grid) stay cheap because list identity does not cause full re-render.
  • SolidStart server functions give a typed RPC surface alongside the Effect backend; both rely on the same shared schemas.
🗄️

Database

PostgreSQL (managed). Relational planning data + jsonb for note bodies and flexible attributes, with indexes tuned for sync pulls.

📦

Local-first

Client IndexedDB mirror + outbox queue. Solid stores hydrate from the local mirror first, then reconcile with the server.

🔔

Push

Web Push (VAPID) delivered by Effect services on the backend and received by a service worker; Solid UI shows missed-reminder inbox on next open.

3Monorepo layout (proposed)

Structure that keeps the Effect backend, Solid frontend, and shared domain in one tree while preserving hard boundaries.

tali/ ├── apps/ │ ├── web/ # SolidStart (SolidJS v2 RC) client + SSR shell │ └── api/ # Effect HTTP/RPC server, jobs, push dispatch ├── packages/ │ ├── domain/ # Effect Schema entities, invariants, typed errors │ ├── sql/ # @effect/sql tables, migrations, query helpers │ ├── rpc/ # Effect RPC contracts consumed by web + api │ ├── config/ # typed env + Alchemy-bound configuration │ └── ui/ # Solid design-system components + tokens ├── infra/ # Alchemy v2 stacks (per environment) ├── turbo.json └── pnpm-workspace.yaml
Rule that keeps it maintainable

Solid components never import Effect services directly; they call RPC contracts from packages/rpc. Effect services never import Solid. The shared domain package is the only mutual dependency. This is what makes later frontend or backend swaps low-risk.

4Scope boundary — Must only

Everything below is included only because the PRD labels it Must. Items explicitly moved later are listed so no one plans for them accidentally.

7Backend catalog (Effect services & data)

The concrete backend surface required to support every Must item. All entities share the common item fields (id, type, title, owner, status, dates, tags, version, deletedAt) so sync, search and trash work uniformly.

Domain aggregates

  • User, Household, Membership — auth and shared space.
  • Habit + HabitEntry — definition and daily logging.
  • Event (+ occurrence exceptions) and Occasion.
  • Task (+ recurrence linkage).
  • Reminder + ReminderDispatch.
  • Note + Tag relations.
  • List + ListItem.
  • Project, shared across tasks and lists where useful.

Effect services (Layers)

  • AuthService — sessions, password hashing, authorization context.
  • HouseholdService — shared-space membership and sharing.
  • HabitService, TaskService, EventService, ReminderService, NoteService, ListService.
  • RecurrenceService — RRule expansion shared by events/tasks.
  • CalendarService — Jalali-safe expansion and range queries.
  • SyncService — cursor pulls, outbox pushes, change feed, SSE wake-ups.
  • NotificationService — Web Push dispatch + cron orchestration.
  • SearchService — notes full-text and filtering.
  • TrashService — soft delete, restore, purge.

Data & sync contracts

ConcernImplementation in Effect terms
Schema & validation@effect/schema defines every entity, request and event; encoders/decoders are reused by packages/rpc, HTTP handlers and tests.
Persistence@effect/sql repositories with explicit migrations; time instants as timestamptz, all-day as date + IANA timezone.
Sync orderingMonotonic per-row version plus updatedAt; cursor pulls by version; push applies atomically and appends a change-feed entry.
Realtime wake-upSSE channel per household; clients pull whenever a wake-up (or reconnect) occurs.
Background workAlchemy v2 cron triggers invoke reminder scan and trash purge through Effect workflow/runners.
ObservabilityEffect tracing/metrics around sync commits, push dispatch latency and reminder delivery.

Essential backend endpoints (conceptual)

  • POST /rpc/* (or SolidStart-calling Effect service methods via shared RPC) for all aggregates.
  • GET /sync/pull?cursor and POST /sync/push with batched outbox entries.
  • GET /sse/household for wake-ups.
  • POST /push/register, plus Web Push dispatch internal path.
  • GET /search/notes?q with Persian-normalized FTS.
  • GET /today, GET /week, GET /month aggregated read models.

SolidJS implementation notes for Must features

  • Reactivity: signals for section order, filters, and connection status; stores for cached task/habit/item collections with structural identity to avoid needless DOM churn.
  • Data fetching: use a Solid-compatible server-state cache; hydrate from IndexedDB first, then RPC.
  • Mutations: writeLocal() transaction first; UI already updated; sync runs in background and surfaces failures in a non-blocking banner.
  • Resilience: local draft recovery for notes; pending-outbox indicator; replay on reconnect.
  • Touch/keyboard: 44px targets; drag with touch and keyboard equivalents; reduced-motion respected.
  • i18n/copy: Persian copy curated, not literal; bidirectional text handled for mixed Persian/English titles.
